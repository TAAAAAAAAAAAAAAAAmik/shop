# Kinetix

Telegram-бот магазина цифровых товаров: каталог, внутренний баланс, автовыдача
товара из склада, оптовые цены, промокоды, рефералка и админка.

Python 3.11 · [aiogram 3](https://docs.aiogram.dev) · SQLAlchemy 2 (async) ·
SQLite или PostgreSQL.

---

## Возможности

**Покупателю**
- Каталог: категории → товары → карточка с ценой, остатком и оптовыми ступенями
- Внутренний баланс, два способа пополнения на выбор:
  - криптой через [@CryptoBot](https://t.me/CryptoBot) — зачисление автоматическое
  - переводом по реквизитам (карта, СБП) — вы подтверждаете вручную
- Мгновенная автовыдача: код/ссылка приходит сразу после списания, пачка от 100 шт. — файлом
- Оптовые цены: чем больше количество, тем ниже цена за штуку
- Промокоды с ограничением по числу использований и по пользователю
- Реферальная программа: процент с каждого пополнения приглашённого
- История покупок и операций по балансу
- Два языка: RU / EN, переключаются на лету

**Администратору**
- Очередь заявок на перевод: подтвердить или отклонить в один тап
- Реквизиты для переводов редактируются прямо в боте, без передеплоя
- Статистика: пользователи, заказы, выручка, деньги на балансах
- Залив склада текстом или файлом `.txt` с автоматическим отсевом дублей
- Ручная корректировка баланса (начисление и списание)
- Создание промокодов одной строкой
- Рассылка по всей базе с учётом лимитов Telegram
- Уведомления о каждом заказе и пополнении

## Быстрый старт

```bash
git clone <repo> && cd shop
make install                 # venv + зависимости
cp .env.example .env         # вписать BOT_TOKEN и ADMIN_IDS
make seed                    # демо-каталог (необязательно)
make run
```

Минимум, который нужен в `.env`:

```env
BOT_TOKEN=123456789:AA...    # у @BotFather
ADMIN_IDS=123456789          # свой ID подскажет @userinfobot
```

Способы оплаты включаются независимо:

- **Перевод по реквизитам** работает сразу, как только реквизиты заданы — через
  `MANUAL_REQUISITES` или в боте: «Админка → Реквизиты».
- **Криптой** — когда задан `CRYPTO_PAY_TOKEN`.

Если не настроено ничего, бот работает в режиме «только каталог», а баланс
начисляется руками через админку.

### Docker

```bash
cp .env.example .env
docker compose up -d --build
```

`docker-compose.yml` поднимает бота вместе с PostgreSQL. Для SQLite уберите
сервис `db` и оставьте `DATABASE_URL` по умолчанию.

## Конфигурация

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `BOT_TOKEN` | — | Токен бота, обязателен |
| `ADMIN_IDS` | пусто | ID админов через запятую |
| `SHOP_NAME` | `Kinetix` | Название в текстах |
| `SUPPORT_USERNAME` / `CHANNEL_USERNAME` / `REVIEWS_USERNAME` | пусто | Ссылки в разделе «Поддержка» |
| `DATABASE_URL` | `sqlite+aiosqlite:///data/kinetix.db` | БД |
| `CURRENCY` | `RUB` | Валюта магазина |
| `MIN_TOPUP` / `MAX_TOPUP` | `5000` / `10000000` | Границы пополнения, **в копейках** |
| `REFERRAL_PERCENT` | `5` | Процент рефереру с пополнения |
| `MANUAL_PAYMENT_ENABLED` | `true` | Разрешить перевод по реквизитам |
| `MANUAL_REQUISITES` | пусто | Реквизиты по умолчанию; в боте перекрываются |
| `MANUAL_TTL_MINUTES` | `180` | Сколько живёт заявка до нажатия «Я оплатил» |
| `CRYPTO_PAY_TOKEN` | пусто | Токен Crypto Pay API |
| `CRYPTO_PAY_TESTNET` | `false` | Тестовая сеть CryptoBot |
| `PAYMENT_POLL_INTERVAL` | `15` | Как часто опрашивать счета, сек |
| `INVOICE_TTL_MINUTES` | `60` | Срок жизни счёта |
| `DEFAULT_LOCALE` | `ru` | Язык по умолчанию |
| `THROTTLE_RATE` | `0.4` | Минимальный интервал между действиями юзера, сек |

## Как это устроено

```
kinetix/
├── config.py         настройки из окружения
├── money.py          деньги: парсинг, форматирование, проценты
├── i18n.py           словарный переводчик
├── locales/          ru.py / en.py
├── db/
│   ├── base.py       движок, фабрика сессий
│   ├── models.py     схема
│   └── seed.py       демо-каталог
├── services/         вся бизнес-логика, без Telegram
│   ├── wallet.py     изменения баланса + реестр
│   ├── orders.py     котировка и покупка
│   ├── topups.py     пополнения обоих типов, идемпотентное зачисление
│   ├── payments.py   опрос счетов CryptoBot
│   ├── cryptobot.py  клиент Crypto Pay API
│   ├── promo.py      промокоды
│   ├── catalog.py    каталог и склад
│   ├── settings_store.py  настройки, редактируемые из бота
│   └── users.py      пользователи, рефералы
├── handlers/         только Telegram: разбор ввода и отрисовка
├── keyboards/        инлайн-клавиатуры и типизированные callback-данные
├── middlewares/      сессия БД, пользователь, троттлинг
└── __main__.py       сборка приложения
```

Хендлеры ничего не считают — они разбирают ввод и зовут сервис. Вся логика
денег лежит в `services/`, поэтому её можно тестировать без Telegram, чем и
занимается `tests/`.

### Деньги

Все суммы — **целые минорные единицы** (копейки/центы). Никаких `float`:
`1000` означает `10.00 ₽`. Парсинг и вывод — только через `kinetix/money.py`.

Баланс меняется исключительно через `services/wallet.py`, который вместе с
новым балансом пишет строку в `balance_txs`. Реестр append-only, так что любую
сумму можно объяснить постфактум.

### Почему один код нельзя продать дважды

Покупка целиком идёт в одной транзакции: резерв позиций склада, списание с
баланса, создание заказа. Любая ошибка откатывает всё.

- **PostgreSQL** — `SELECT ... FOR UPDATE SKIP LOCKED`, два параллельных
  покупателя физически не увидят одну и ту же строку склада.
- **SQLite** — блокировок строк нет, поэтому критическая секция сериализуется
  через `asyncio.Lock` в процессе. Для одного процесса, ради которого SQLite и
  берут, этого достаточно.

Тест `test_concurrent_buyers_never_share_a_key` запускает 10 покупателей на 5
ключей: ровно пятеро получают товар, дублей нет.

### Полуавтоматический перевод по реквизитам

Для оплаты рублями переводом бот ведёт заявку с явным статусом:

```
pending ──[покупатель: «Я оплатил»]──► awaiting_review ──┬─[вы: подтвердить]─► paid
   │                                                     └─[вы: отклонить]───► rejected
   └─[отмена или истёк TTL]──► cancelled / expired
```

1. Покупатель выбирает «Перевод по реквизитам» и вводит сумму.
2. Бот показывает реквизиты и **код заявки** вида `KNX-7F3A2B` — его просят
   указать в комментарии к переводу. Код без символов `0/O/1/I`, чтобы его
   нельзя было прочитать неоднозначно.
3. После перевода покупатель жмёт «Я оплатил», заявка уходит в очередь, а вам
   сразу приходит карточка с покупателем, суммой, кодом и кнопками
   «Подтвердить» / «Отклонить».
4. Вы сверяете поступление в банке и жмёте кнопку. При подтверждении баланс
   пополняется и покупателю уходит уведомление, при отклонении — не
   пополняется, покупателю приходит отказ со ссылкой на поддержку.

Защиты, которые тут важны:

- **Одна открытая заявка на пользователя.** Иначе два перевода на одинаковую
  сумму невозможно развести по заявкам.
- **Подтвердить можно только заявку, которую покупатель заявил оплаченной.**
  Просто созданную (`pending`) подтвердить нельзя.
- **Двойное подтверждение не проходит.** Если два админа нажмут «Подтвердить»
  одновременно, деньги зачислятся один раз — см. ниже.
- **Заявка на проверке не сгорает по TTL.** Чистятся только невостребованные.

Реквизиты меняются в «Админка → Реквизиты» и хранятся в БД, так что смена
карты не требует передеплоя.

### Почему пополнение не зачислится дважды

Каждая смена статуса — условный `UPDATE ... WHERE status = <ожидаемый>`.
Второй вызов увидит `rowcount = 0` и просто выйдет. Поэтому ни повторный
вебхук, ни совпавший тик поллера, ни нажатие «Проверить оплату», ни два
админа, одновременно нажавшие «Подтвердить», не могут начислить деньги
дважды. Путь зачисления общий для обоих способов оплаты — различается только
статус, из которого разрешён переход.

Оплата опрашивается поллером, а не вебхуком, — боту не нужен публичный HTTPS.
Когда вебхук понадобится, менять придётся только точку входа: `services/payments.settle()`
остаётся тем же.

## Разработка

```bash
make test     # pytest
make lint     # ruff
make fmt      # ruff --fix
```

Тесты покрывают денежный путь целиком: арифметику, покупку и её откаты, гонку
за складом, идемпотентность пополнений, конечный автомат ручных заявок,
рефералку, промокоды, паритет RU/EN.

`tests/test_bot_flow.py` и `tests/test_manual_flow.py` прогоняют настоящие
Telegram-апдейты через настоящий диспетчер с подменённой сессией Telegram — от
`/start` до выдачи товара и от заявки на перевод до подтверждения админом.

### Схема БД

Схема создаётся через `create_all()` при старте. Перед первым продакшен-
релизом подключите Alembic: сейчас изменения моделей не мигрируют существующую
базу автоматически.

## Эксплуатация

- **Бэкапьте базу.** В ней остатки склада, балансы и заявки — это деньги.
- **Сверяйте переводы сами.** Кнопка «Подтвердить» верит вам, а не банку:
  бот не имеет доступа к выписке и не может проверить поступление за вас.
- **Не держите `.env` в git.** Он уже в `.gitignore`.
- **Один процесс на SQLite.** Нужно масштабирование — переезжайте на PostgreSQL,
  там блокировки строк делают покупку безопасной для нескольких воркеров.
- Продавайте только то, на что у вас есть право: перепродажа чужих промо-ссылок
  и аккаунтов нарушает условия поставщиков и заканчивается блокировками и
  возвратами — в первую очередь у вас как у продавца.
